# Production operation

Shared mode uses a D1 binding named `DB`. Independent builds work in `local` mode, but their readiness reports say shared production controls are unconfigured. Questions, addresses, excerpts and conversation state never enter this database.

## Shared limits

| Limit | Default |
| --- | --- |
| Requests per client | 12/minute |
| Requests across instances | 120/minute; 5,000/UTC day |
| Concurrent API requests | 8 total; 2/client |
| Outbound reads | 40/request; 400/minute; 10,000/UTC day |
| Optional model calls | 100/UTC day |
| API execution, including admission | 30 seconds |
| Database operation | 2 seconds |
| Abandoned request lease | 45 seconds |

Admission and counter updates share one [D1 batch transaction](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). Conditional writes prevent separate Worker instances from oversubscribing counters and leases. Completed requests release their leases; expired leases recover after crashes. Client concurrency counts both minute keys across a minute boundary. Invalid shared configuration and database failures refuse requests instead of silently switching to local counters.

The trusted Cloudflare ingress address is transformed with a secret HMAC and the current minute; raw addresses are not stored. Missing ingress addresses share a bucket. Arbitrary `X-Forwarded-For` is not used. Limits return 429 and `Retry-After`; exhausted outbound budgets, unavailable storage and maintenance return 503. The absolute request deadline returns 504, propagates cancellation and blocks later outbound calls, including when an adapter catches errors. Existing body-read and response-byte limits remain separate.

Outbound counts cover uncached GIS/development reads and model calls. Model limits count requests, not billed tokens or currency. Keep inference disabled until the chosen provider's output/account spending caps have been configured and evaluated. These controls apply after Worker dispatch; platform connection handling, network floods and billing ceilings remain hosting responsibilities.

## Deployment configuration

Sites uses `d1: "DB"` in the existing `.openai/hosting.json`. The package includes `drizzle/0000_operations.sql`, generated by `node scripts/generate-operations-schema.mjs` from the same idempotent schema used by runtime initialization. Independent operators create their own D1 database and add a `DB` binding to their preserved Wrangler config.

Set server-side runtime values through the host:

- `TAMPABAYBOT_OPERATIONS_MODE=shared`.
- `TAMPABAYBOT_LIMIT_SECRET`: a random secret of at least 32 characters.
- `TAMPABAYBOT_MONITOR_TOKEN`: a separate random secret of at least 32 characters.
- `TAMPABAYBOT_MAINTENANCE=0`; set `1` to pause resident APIs during an incident.

Never put secrets in source, public build variables or hosting JSON. Limit overrides use `TAMPABAYBOT_LIMIT_` followed by `CLIENT_PER_MINUTE`, `REQUESTS_PER_MINUTE`, `REQUESTS_PER_DAY`, `CONCURRENCY`, `CLIENT_CONCURRENCY`, `OUTBOUND_PER_REQUEST`, `OUTBOUND_PER_MINUTE`, `OUTBOUND_PER_DAY` or `MODEL_PER_DAY`. Invalid values fail closed. This is a fixed-window policy, not uniformly spaced admission.

## Health and alerts

`/api/health` is cheap HTTP-200 liveness with an honest readiness report. It distinguishes fresh, stale, unavailable, missing and invalid evidence. Intentional `live-query-only` sources are counted separately; this endpoint does not verify publishers or GIS uptime. `/api/ready` returns 200 only for `ready: true`, otherwise 503. Public probes make no D1 calls and report `authenticated_probe_required` for database readiness. Supply `Authorization: Bearer <TAMPABAYBOT_MONITOR_TOKEN>` for a fresh database check.

The same token protects `/api/operations`, which returns aggregate 15-minute request/error/limit/duration counts and active leases. Wrong/missing tokens receive 404. Private Sites additionally requires its existing Sites gate header.

The `Service operations monitor` workflow runs approximately every 15 minutes and supports manual dispatch when repository variable `TAMPABAYBOT_MONITOR_ENABLED` is `true`. It defaults to disabled, so an unconfigured fork or checkout does not claim a monitoring pass. GitHub schedules are best-effort. Configure repository secrets `TAMPABAYBOT_MONITOR_URL` (HTTPS origin), `TAMPABAYBOT_SITE_TOKEN` (private Sites only), and `TAMPABAYBOT_MONITOR_TOKEN`, then enable the variable. Exporting private hosting credentials to another service requires the owner's authorization. The script follows no redirects and emits no URL, token or resident input. Failed runs signal degraded readiness, at least three errors representing 10% of requests, at least ten limited requests, any request taking 25 seconds, or monitor failures. The alert channel is the repository owner's GitHub Actions failure notifications; no unverified email/webhook is configured.

Metrics have five-minute buckets and a seven-day retention target. Admission and monitor runs delete expired counters/leases; requests and monitor runs delete expired metrics. This is explicit cleanup, not D1 TTL: without traffic or a working monitor, expired rows remain until the next cleanup. The repository disables Worker observability; platform/proxy logs and provider retention remain separate policies, not a zero-logging claim.

## Incident and rollback procedure

The site/repository owner is the initial operator. Private vulnerability reporting uses [SECURITY.md](../SECURITY.md); there is no staffed response-time commitment.

1. Inspect the monitor alert and private aggregate metrics without collecting resident request bodies.
2. For abuse, dependency failure or suspected disclosure, enable maintenance, preserve private access and reduce limits as appropriate. Health and protected monitoring remain available.
3. Redeploy the previous known working Sites version for a code regression. Independent operators use the Wrangler version commands in [deployment](DEPLOYMENT.md). Evidence rollback follows [source updates](SOURCE_UPDATES.md).
4. Rotate affected runtime and monitor secrets. Retain version/generation, timing and aggregate errors without resident data.
5. Verify access, protected readiness, ordinary and limited requests, selected question/property flows, and monitoring before clearing maintenance. Record unavailable sources separately.

Source-age alerts require reviewed acquisition. Rebuilding the same snapshots does not make them fresh. Passing software checks do not replace independent human or screen-reader review.
