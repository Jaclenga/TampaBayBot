# Production operation

Shared mode uses a D1 binding named `DB`. Independent builds work in `local` mode, but their readiness reports say shared production controls are unconfigured. Questions, addresses, excerpts and conversation state never enter this database.

## Shared controls

Before framework dispatch, the Worker accepts GET/HEAD navigation and JSON POSTs only at the exact `/api/ask`, `/api/location`, `/api/property` and `/api/development` paths. Other methods or POST paths return 405; non-JSON bodies at those input paths return 400. Unused server-action headers return 404. These refusals occur before reading the body, so page/form/action uploads cannot reach the framework's form parser or bypass the bounded API readers. Supported API requests continue through the shared controls below.

Shared mode coordinates request rates, client and service concurrency, outbound reads and optional model calls across Worker instances. Request and database timeouts limit how long the service waits for work; expiring leases recover capacity after interrupted requests. Invalid shared configuration and database failures refuse requests instead of silently switching to local counters.

Client limits use temporary identifiers derived from trusted Cloudflare ingress addresses with a server-side secret; raw addresses are not stored. Request limits return 429 with `Retry-After`. Exhausted outbound budgets, unavailable storage and maintenance return 503; the request deadline returns 504. Clients should respect these responses and avoid immediate retry loops.

Outbound counts cover uncached GIS/development reads and model calls. Model limits count requests, not billed tokens or currency. Keep inference disabled until the chosen provider's output/account spending caps have been configured and evaluated. These controls apply after Worker dispatch; platform connection handling, network floods and billing ceilings remain hosting responsibilities.

## Deployment configuration

Create a D1 database and configure a `DB` binding in the host's deployment configuration. The package includes `drizzle/0000_operations.sql`, generated by `node scripts/generate-operations-schema.mjs` from the same idempotent schema used by runtime initialization. For independent deployments, add the binding to the Wrangler configuration described in [deployment](DEPLOYMENT.md).

Set server-side runtime values through the host:

- `TAMPABAYBOT_OPERATIONS_MODE=shared`.
- `TAMPABAYBOT_LIMIT_SECRET`: a random secret of at least 32 characters.
- `TAMPABAYBOT_MONITOR_TOKEN`: a separate random secret of at least 32 characters.
- `TAMPABAYBOT_MAINTENANCE=0`; set `1` to pause resident APIs during an incident.

Never put secrets in source, public build variables or hosting JSON. Configure deployment-specific request, concurrency, outbound and model-call budgets through host runtime settings. Limit overrides use `TAMPABAYBOT_LIMIT_` followed by `CLIENT_PER_MINUTE`, `REQUESTS_PER_MINUTE`, `REQUESTS_PER_DAY`, `CONCURRENCY`, `CLIENT_CONCURRENCY`, `OUTBOUND_PER_REQUEST`, `OUTBOUND_PER_MINUTE`, `OUTBOUND_PER_DAY` or `MODEL_PER_DAY`. Values must be positive integers within the implementation's supported range; invalid values fail closed. Rate limits use fixed windows. Execution deadlines, database timeouts and lease duration are implementation settings, with no runtime overrides.

Review budgets against expected traffic, hosting capacity and provider spending caps before enabling shared service. Keep deployment-specific values in host configuration and verify the effective limits through authenticated operations metrics.

## Health and alerts

`/api/health` is cheap HTTP-200 liveness with an honest readiness report. It distinguishes fresh, stale, unavailable, missing and invalid evidence. Intentional `live-query-only` sources are counted separately; this endpoint does not verify publishers or GIS uptime. `/api/ready` returns 200 only for `ready: true`, otherwise 503. Public probes make no D1 calls and report `authenticated_probe_required` for database readiness. Supply `Authorization: Bearer <TAMPABAYBOT_MONITOR_TOKEN>` for a fresh database check.

The same token protects `/api/operations`, which returns aggregate 15-minute request/error/limit/duration metrics, active leases and configured limits. Wrong/missing tokens receive 404. Deployments with a hosting access gate also require its credential.

The `Service operations monitor` workflow runs approximately every 15 minutes and supports manual dispatch when repository variable `TAMPABAYBOT_MONITOR_ENABLED` is `true`. It defaults to disabled, so an unconfigured fork or checkout does not claim a monitoring pass. GitHub schedules are best-effort. Configure repository secrets `TAMPABAYBOT_MONITOR_URL` (HTTPS origin), `TAMPABAYBOT_SITE_TOKEN` (only for Sites deployments requiring an access token), and `TAMPABAYBOT_MONITOR_TOKEN`, then enable the variable. Keep monitoring URLs and credentials in the secret store. The script follows no redirects and emits no URL, token or resident input.

Failed runs signal degraded readiness, elevated errors, repeated request limiting, slow requests or monitor failures. Review the monitor script's alert rules for the deployment; they do not have runtime configuration overrides. The alert channel is the repository owner's GitHub Actions failure notifications. Verify those notifications reach the responsible operator.

Metrics have five-minute buckets and a seven-day retention target. Admission and monitor runs delete expired counters/leases; requests and monitor runs delete expired metrics. This is explicit cleanup, not D1 TTL: without traffic or a working monitor, expired rows remain until the next cleanup. The repository disables Worker observability; platform/proxy logs and provider retention remain separate policies, not a zero-logging claim.

## Incident and rollback procedure

The site/repository owner is the initial operator. Private vulnerability reporting uses [SECURITY.md](../SECURITY.md); there is no staffed response-time commitment.

1. Inspect the monitor alert and private aggregate metrics without collecting resident request bodies.
2. For abuse, dependency failure or suspected disclosure, enable maintenance, verify deployment access controls and reduce limits as appropriate. Health and protected monitoring remain available.
3. Redeploy the previous known working version for a code regression. Wrangler version commands are in [deployment](DEPLOYMENT.md). Evidence rollback follows [source updates](SOURCE_UPDATES.md).
4. Rotate affected runtime and monitor secrets. Retain version/generation, timing and aggregate errors without resident data.
5. Verify access, protected readiness, ordinary and limited requests, selected question/property flows, and monitoring before clearing maintenance. Record unavailable sources separately.

Source-age alerts require reviewed acquisition. Rebuilding the same snapshots does not make them fresh. Passing software checks do not replace independent human or screen-reader review.
