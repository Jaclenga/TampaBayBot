# Verifying housing-crisis resources

The [static resource catalog](../pages-demo/src/housing-resources.json) serves the Cloudflare Pages directory and deterministic crisis plans. It remains accessible without Workers AI, D1 or the backend Worker. The catalog is a set of checked public navigation records, not a live vacancy, funding, appointment or eligibility feed. Its [record-level provenance notes](../pages-demo/src/HOUSING_RESOURCES.md) identify the sources checked in the current revision.

## Record meaning

Each record has a stable `id`, official HTTPS `url`, and `sourceUrl` for the page supporting its public claims. It also identifies an organization and program, crisis categories, geographic coverage, a short description, eligibility and restrictions, and public contact information. An `intakeUrl` or `serviceHours` is included only when a source explicitly supports it. Municipality restrictions are separate from county coverage; a City of Tampa program must not appear as a countywide entitlement.

`verifiedAt` is the last **substantive human review** of the cited public page and contact listing. `verificationStatus` distinguishes `source_checked`, `needs_recheck` and `source_unavailable`; it does not mean the contributor phoned the agency. `nextReviewAt` is the configured date for another content review. `lastLinkCheckedAt` and `linkStatus` describe automated link checks only. An optional `reviewedContentHash` is a baseline from a human-reviewed page; an unset baseline means automated comparison cannot yet say whether that page changed. `knownIssues` and `reviewNotes` explain unresolved conflicts and reviewer findings. These fields are part of the public catalog: never put private case details, resident questions, credentials, or unlisted contacts in them.

`availabilityStatus` distinguishes `unknown`, `confirmed_open`, `temporarily_closed` and `discontinued`. Use `confirmed_open` only for an explicitly verified current program or intake state, with a source and date. A published phone number, application instructions, or a working web page alone does not establish open funding, a shelter bed, a waitlist position or approval. If a closure or discontinuation is reported, retain its source and date rather than silently deleting the history. In particular, an HTTP 200 response cannot update `verifiedAt`, `verificationStatus`, `availabilityStatus`, eligibility, deadlines or contact details.

When the answer path cites a retrieval source with `known_issues`, it surfaces those notes as answer warnings for that cited source. Keep those notes short, public, and specific; a warning does not make an unsupported claim safe to publish.

Changing service and intake contacts use a 30-day `refreshDays` interval; stable court and public legal-information pages use 90 days. `nextReviewAt` can bring a review forward; the earlier of that date and the interval is due. These are review targets, not guarantees of accuracy for the entire interval. A record past its interval is stale and must be labeled for recheck. Plans first use recently checked records. If none match, an older `source_checked` contact may be shown for direct verification when its check is no more than 365 days old; it is copied into the plan with `needs_recheck` status and a warning, never presented as current availability. Closed, discontinued, originally `needs_recheck`, and source-unavailable records remain excluded from plans. The full directory may show stale listings with clear warnings and official links. A successful page fetch never upgrades `availabilityStatus` automatically.

## Automated freshness report

The resource checker reads the static housing catalog, the existing [retrieval source registry](../data/sources.json), and authored GIS/development endpoint configuration. The endpoint records use an `operational` catalog and are checked for link status only. Their authority is recorded independently for each endpoint: official GIS and government development links are distinct from the independent development snapshot repository. Reachability never verifies the returned GIS data or project status, and no factual review date is inferred for these endpoints. Offline mode lists stable IDs, dates, review status, and overdue reviews without network access:

```sh
npm run resource:freshness -- --output work/resource-freshness/local
```

For the full live report, first use the existing source pipeline to stage retrieval sources. Pass its metadata-only report to the checker so retrieval content-change signals come from that acquisition, without a second content ingestion:

```sh
npm run source:stage -- --output work/source-refresh/local-review
npm run resource:freshness -- --live --allow-network --source-stage-report work/source-refresh/local-review/report.json --output work/resource-freshness/local-live
```

The live checker defaults to four concurrent requests, a one-second interval between requests to the same host, and seven days of grace after a factual review becomes due. It attempts a URL at most three times (`--max-attempts 3`), with an eight-second deadline per attempt (`--timeout-ms 8000`) and a 30-second total URL budget (`--total-timeout-ms 30000`). `--concurrency`, `--host-interval-ms`, and `--review-grace-days` adjust the other bounds for a local run. Add `--fail-on-actionable` when a local or separate CI gate should exit with code `2` after writing reports that contain actionable findings. The weekly workflow leaves that flag off so its issue job can triage completed reports; an acquisition or report-generation failure still fails the relevant job.

Read `report.md` for the attention list and `report.json` for resource IDs, URL results, and reasons. An offline `link_not_checked` reason means no checked-in automated observation exists; it is not a broken-link finding. The checker distinguishes a confirmed missing page from timeouts, rate limits, and other temporary failures. It records redirects for review and flags possible content changes; a changed page may reflect layout or publisher updates rather than a changed rule. With no reviewed baseline, the static catalog has no historical content comparison yet. Neither a reachable link nor an unchanged page proves that a program still has funding, a bed, a current deadline, accurate contact details, or eligibility for a particular person. Live checks use public URLs only; the report must not include downloaded page text, resident questions, or personal information.

Each `report.resources[]` entry has a `factual_verification` object. Its `eligibility`, `hours`, and `contact_details` values remain `not_checked_by_monitor` even after a successful link check. Substantive review of those facts remains a human task.

The [scheduled source-refresh workflow](../.github/workflows/source-refresh.yml) stages retrieval sources, then runs the live checker each Monday and retains both metadata-only reports for 14 days. It does not edit the registries, approve a source update, publish a Pages build, or deploy. The live checker is read-only: its observed check time, status, redirect, and content-change signals appear in ignored reports until a maintainer copies supported metadata into a reviewed repository edit. An empty `lastLinkCheckedAt` in the repository does not mean the scheduled checker never ran; consult the dated workflow artifact.

### Weekly issue triage

The version 2 `report.json` contains an `actionable` list with stable fingerprints for findings that warrant review. The weekly workflow creates one open issue per fingerprint with the `source-monitor` label. A later run updates its generated block only when the finding details change, preserving maintainer notes outside that block. It does not close issues automatically; close them after reviewing the original source and correcting or documenting the record. Issue synchronization runs only when freshness report generation succeeds; the source-refresh job still retains any available artifacts if generation fails.

Actionable signals include a confirmed 404/410, an invalid or unsafe URL, a permanent 301/308 redirect, a temporary redirect with a missing destination or HTTPS downgrade, a potential content change, and a factual review overdue beyond the configured grace period. Permanent redirects need publisher review because source acquisition rejects redirects and the configured URL may need a reviewed update. Rate limits, timeouts, 5xx responses, and other transient acquisition failures remain in the report for follow-up but do not create issues from a single run. A fingerprint is a deduplication key, not proof that the source's program details changed. Issue bodies contain stable resource IDs and brief status summaries; consult the metadata-only workflow artifact for the full observation. Automated issues never update `verifiedAt`, program availability, eligibility, deadlines, or the deployed corpus.

## Contributor workflow

1. Triage each report entry by stable resource ID. Reopen a redirected link and check the destination is still the same official publisher before changing `url`, `sourceUrl`, or the registry's `canonical_url`. Treat a timeout, rate limit, or temporary server failure as unresolved and retry later; do not mark it confirmed broken. If a page is missing, seek a replacement official page or direct provider confirmation and retain the issue until resolved.
2. Compare any changed page with the current public claims. Find the publisher's official program or intake page and confirm the organization, program name, geographic coverage, public contact, eligibility, restrictions, hours, and any application route. A fingerprint or HTTP status is a prompt to review, not a content approval. Check deadline language against current official material and the visitor's required context. Contact providers directly for capacity or funding; do not infer either from a working page.
3. Resolve conflicts between official pages before publishing a claim. Record the conflict in `knownIssues` and a short, dated explanation in `reviewNotes`; withhold disputed eligibility or referral claims. Keep the existing stable ID when only a URL changes. Use `unknown` availability unless the cited source establishes a dated current status. Never silently replace an official source with an unrelated redirect target.
4. Update only the records actually reviewed. For the housing catalog, set `verifiedAt`, `verificationStatus`, and `nextReviewAt` after a substantive review; keep `refreshDays` aligned with the chosen interval. Establish `reviewedContentHash` only from page content actually reviewed, not from an unattended run. Transcribe link-check time and result separately into `lastLinkCheckedAt` and `linkStatus`. Leave `verifiedAt` unchanged after a link-only check. If a source cannot support its existing claims, set `needs_recheck` or `source_unavailable` and correct or withhold the affected text.
5. For the retrieval registry, use the existing [source staging and approval process](SOURCE_UPDATES.md). A flagged `canonical_url` or changed program page requires a local `source:stage`, `source:review --local-diff`, and human approval of the exact candidate before `source:apply`. Record `last_content_reviewed_at`, `review_status`, `next_review_at`, `last_link_checked_at`, `link_status`, `known_issues`, and `review_notes` in its source record only as supported by that review. The initial source-only checkout has no human-review dates for these retrieval records; do not backfill them from automated retrieval. A link check never approves new evidence chunks or citations.
6. Run the resource data tests, crisis evaluation suite and Pages browser test with the API disabled before a Pages change. Manually open key official links on a phone-size browser and verify copy/print, language and emergency access. A crawler response alone does not prove how a public browser will behave. Deploy only through the separate reviewed release process.

Do not copy private case details, intake submissions, client names, unlisted numbers or source-page prose into the catalog. Never add an unverified shelter opening or funding amount. Source review can identify an error in a listing; correcting the listing does not change the separately reviewed RAG corpus. See [source updates](SOURCE_UPDATES.md) for that pipeline and [safety limitations](SAFETY_AND_LIMITATIONS.md) for public-use boundaries.
